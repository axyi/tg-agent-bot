Status: ready for `go`.
Base: `v1.8.0` (tagged 2026-09-10, `ee09c4d`; `main` at `3b145d8` carries
three docs-only commits on top). Nothing about v1.8.0 is reopened.
Target version: **1.9.0** — MINOR, because the release adds user-facing

One subject, the course's assignment 6 in full, bonuses included: a user
sends the bot a `.txt`, `.md`, `.docx` or `.pdf`; the bot extracts the text,
chunks it, embeds it through LM Studio's OpenAI-compatible embeddings
endpoint, stores chunks and vectors in the existing SQLite file behind
`sqlite-vec`, and the agent answers later questions through one new tool,
`search_documents(query)`, whose results are hybrid (vector + BM25, fused by
RRF), reranked by the LLM, and attributed to a filename and, for PDFs, a page.
The grading rubric is `/home/akh/aihome/coders-su/base/assignments/06-rag-for-agent.md`
(Russian) — cited as the **provenance** of the requirement list and **not read
by the run** (EC-01's boundary); the assignment's items are restated in
Appendix A's assignment traceability, which is the run's only source.
Appendix A's extra column and that table map every one of its 15 requirement
points, 18 acceptance items and 5 bonuses to a requirement here.

Requirement ids group by subject (`DOC` ingest, `STO` storage, `RET`
embeddings and retrieval, `TOOL` the agent tool, prompt and attribution, `CMD`
Telegram flow and commands, `ERR` the error matrix, `SEC`, `EVAL`, `TST`) and
by release mechanics (`EC` execution contract, `VER`, `RPT`, `REV`). The

Two new modules: `documents.py` (extraction, chunking, indexing) and

**REQ-V190-DOC-01 (MUST) — type by lowercase extension; the filename
contract.** `documents.classify(filename: str) -> str | None` returns one of
`"txt"`, `"md"`, `"docx"`, `"pdf"` from the **lowercase extension alone**
(`Report.PDF` → `pdf`), `None` otherwise — MIME type, magic bytes and
Telegram's `mime_type` are never consulted. `documents.clean_filename(raw:
str | None) -> str | None`: `None` or empty → `None`; path separators (`/`,
`\`) and every control character (`ord < 32`, `0x7f`) are removed; the result
is stripped and cut to **120 characters**; an empty result is `None`. The
cleaned name is the `documents.filename` of STO-02, the `/documents` display
name, the `/delete` match key and the attribution string — one value, four
uses.

**REQ-V190-DOC-02 (MUST) — extraction per type, from memory.**
`documents.extract(data: bytes, file_type: str) -> Extracted`. The two
dataclasses are defined **exactly once, here**, both frozen:
`ExtractedPage(text: str, page: int | None)` — `page` is the PDF's 1-based
physical page number and `None` for every other type — and
`Extracted(pages: tuple[ExtractedPage, ...], page_numbered: bool)`. There is
no parallel `page_numbers` field and no `tuple[str, ...]` form anywhere.
Rules:

- `txt`, `md`: decode `utf-8-sig`; on `UnicodeDecodeError` decode `cp1251`
  (the Russian-Windows fallback; both are standard library codecs); one
  `ExtractedPage(text, page=None)`, `page_numbered=False`. Markdown syntax
  is kept as text — no rendering, no stripping.
- `docx`: **before `python-docx` is called at all**, the bytes are opened
  with `zipfile.ZipFile` and the archive is bounded — at most **2,000**
  members, aggregate uncompressed size at most **50 MiB**, no single member
  over **20 MiB**, aggregate compression ratio (uncompressed ÷ compressed)
  at most **100**; a violation refuses the document through ERR-01 row 5b
  before one byte of XML is parsed. Then `python-docx`
  `Document(io.BytesIO(data))`; the text is every
  body paragraph and every table cell's text **in document order** (walk
  `document.element.body` children, emitting paragraphs and tables as they
  appear), paragraphs joined by `\n`, cells by `\t` inside a row and rows by
  `\n`; one `ExtractedPage(text, page=None)`, `page_numbered=False`.
  `zipfile.BadZipFile`,
  `docx.opc.exceptions.PackageNotFoundError` and `KeyError` are the
  corrupted-DOCX class (ERR-01).
- `pdf`: `pypdf.PdfReader(io.BytesIO(data))`; **before any
  `extract_text()`**, `len(reader.pages)` must be at most **500** — more
  refuses the document through ERR-01 row 5b. Then `page.extract_text()`
  per page, with DOC-04's wall-clock budget checked **between pages** (this
  loop is the bot's own, so the check is the bot's to make); a page whose
  text is empty after `strip()` is **skipped** — it contributes no
  `ExtractedPage` and no chunk, while the pages that remain keep the PDF's
  1-based physical index, so `ExtractedPage.page` is that index and never a
  running count; `page_numbered=True`. **The corruption handler's boundary
  is exact**: only exceptions originating from `PdfReader`, from page
  enumeration or from `extract_text()` map to the corrupted-PDF class
  (ERR-01 row 2). `documents.IndexBudgetExceeded` — raised by DOC-04's
  between-pages budget check **inside this loop** — and every other
  document-limit exception of DOC-04 are raised **outside** that
  `try`, or explicitly re-raised through it (`except IndexBudgetExceeded:
  raise` before the corruption mapping), so a budget or limit failure keeps
  its own ERR-01 row (10c, 5b, 13) and can never be reported as
  `Could not read this PDF file.`

Extraction runs on the bytes in memory; **no temporary file, no `Path`, no
`open()`** anywhere in `documents.py` (T-V190-SEC-04 greps it).

**REQ-V190-DOC-03 (MUST) — chunking is character-based and
paragraph-aware.** `documents.chunk_text(text: str, *, target: int = 1000,
hard_max: int = 1200, overlap: int = 200, minimum: int = 50) ->
list[Chunk]`, `Chunk` a frozen dataclass `(text, char_start, char_end)` with
offsets into the input. The algorithm, normative:

1. Split the text into paragraphs on blank lines (`\n\s*\n`), keeping each
   paragraph's offsets **and the separator text between them**: a chunk's
   `text` is the original slice `text[char_start:char_end]`, so no separator
   is invented, dropped or normalised.
2. The algorithm is **offset-based** — it walks the text once and a chunk is
   a half-open span `[char_start, char_end)`. **A chunk holds at most
   `hard_max` = 1,200 characters in total, always.** After the first chunk
   the **new** material a chunk may take is at most `hard_max - overlap` =
   **1,000** characters, so prefixing the 200-character overlap can never
   push it past 1,200.
3. Within that allowance, paragraphs are accumulated while the result stays
   ≤ `target`; a paragraph that would push it over closes the chunk. A
   single paragraph longer than the allowance is split on sentence ends —
   `. ! ?` followed by whitespace — into pieces ≤ `target`; a sentence still
   longer than the allowance is hard-cut **at the allowance**, never at
   `hard_max`.
4. Each chunk after the first starts with the last `overlap` characters of
   the previous chunk's text, so `char_start` lies inside the previous
   chunk; rule 2's allowance keeps the total ≤ `hard_max`.
5. A final chunk shorter than `minimum` **non-whitespace** characters is
   merged into the previous chunk **only when the merged length stays
   ≤ `hard_max`**; otherwise it stands as its own chunk. A text shorter than
   `minimum` yields one chunk if it has ≥ 20 non-whitespace characters, else
   zero (DOC-04 refuses it).
6. The function is deterministic: same input, same output, no randomness,
   no clock.

**1,200 is the maximum everywhere**, before and after a tail merge; DOC-03,
`README.md`, the tests and `E3` state that one number and no other.

For a PDF, `chunk_text` runs **per page**; a chunk never spans pages and
`chunks.page` (STO-02) is the page's 1-based number; for `txt`/`md`/`docx`
`page` is `NULL`. `chunk_index` is the 0-based position in the document
across pages. `README.md` explains the four numbers and the risks of too-small
(context lost, more chunks to embed, weaker BM25 statistics) and too-large
(irrelevant text dilutes the embedding, fewer distinct hits in K = 5, longer
tool output) chunks (assignment item R2; RPT-05).

**REQ-V190-DOC-04 (MUST) — limits, checked in this order, and the

(1) extracted text over **500,000** characters (sum over pages) → "too

**300 s** from the start of the handler, checked **between stages** —

**"From the start of the handler" has exactly one meaning.**

**The transaction, and what it does not cover.** The whole index is **one
transaction** (`BEGIN IMMEDIATE` … `COMMIT`) opened only after the
last embeddings batch has returned, so a failure at any stage leaves the
database exactly as it was, including the replaced document when this is a

**What the 300 s budget is, exactly.** A check between stages and between

**REQ-V190-STO-03 (MUST) — the 5 → 6 migration slots into the chain, and
it rebuilds `llm_calls`.** `storage.py:70` constrains `llm_calls.purpose`
to `('agent', 'summary')`; RET-06 records rerank calls with purpose

**Why the rebuild is safe here, as a fact of this schema:** no table in
`_SCHEMA` or `_OBSERVABILITY_DDL` declares a foreign key referencing
`llm_calls`, and no trigger exists; the only dependent object is the index
`idx_llm_calls_conv` (`storage.py:96`), which the migration recreates. Belt
and braces regardless, because a future table must not silently break the
migration: foreign keys are disabled across the rebuild — the pragma is a
no-op inside a transaction, so the toggle must stand outside it.

**The 5 → 6 step is normative Python control flow, not a success-only
script.** `conn.executescript(...)` cannot express a rollback: a failure in
the create/copy/drop/rename sequence would leave the explicit transaction
open and the connection with foreign keys **off**, and the `PRAGMA
foreign_keys=ON` that follows a successful `COMMIT` would never run. So
`storage._migrate_5_to_6(conn)` is a function with exactly this shape, and
`_MIGRATION_5_TO_6` is the statement list it executes, never an
`executescript` carrying its own pragmas or transaction control:

```python
def _migrate_5_to_6(conn: sqlite3.Connection) -> None:
    conn.execute("PRAGMA foreign_keys=OFF")   # no transaction is active here
    try:
        conn.execute("BEGIN IMMEDIATE")
        for statement in _MIGRATION_5_TO_6:   # the steps (1)-(3) below
            conn.execute(statement)
        conn.execute("COMMIT")
    except BaseException:
        conn.execute("ROLLBACK")
        raise
    finally:
        conn.execute("PRAGMA foreign_keys=ON")
    assert conn.execute("PRAGMA foreign_keys").fetchone()[0] == 1
    assert conn.execute("PRAGMA foreign_key_check").fetchall() == []
```

`except BaseException` — not `Exception` — so a `KeyboardInterrupt` or a
`SystemExit` mid-rebuild still rolls back; the `finally` restores the pragma
on **every** exit, success or failure; and the two assertions run only on
the success path, where `PRAGMA foreign_keys` MUST read **1** and `PRAGMA
foreign_key_check` MUST return **no rows**. On the failure path the
exception propagates to `init_schema`'s caller with the **schema-5 database
intact and usable** and foreign keys back on — `T-V190-STO-09` injects a
failure mid-rebuild and proves exactly that.

The statement list: (1)
runs `_DOCUMENTS_DDL`; (2) rebuilds `llm_calls` by the documented
rename-copy procedure — `CREATE TABLE llm_calls_v6 (…)` with the **same

**REQ-V190-STO-04 (MUST) — the `rag.embedding` pair, written when the
vector table is born, checked at every start.** A `vec0` table's dimension
is fixed at creation, so the binding moment is creation, not the first
insert: in the same `init_schema` call that first creates `vec_chunks`
(i.e. when `embedding_dim` is not `None` and `bot_state` has no
`rag.embedding` key), `init_schema` writes `bot_state('rag.embedding',
'<EMBEDDING_MODEL>:<EMBEDDING_DIM>')` (`storage.py:178`, `set_state`
`:960`) — it therefore takes `embedding_model: str = ""` as a second
keyword.

**Creation and binding are one transaction.** A crash between a bare
`CREATE VIRTUAL TABLE` and the `bot_state` write would leave `vec_chunks`
orphaned at its old dimension, and `IF NOT EXISTS` would then keep that
stale table while the configured pair was written as if it were new. So
when **no `rag.embedding` key exists**, `init_schema` inspects
`sqlite_master` for `vec_chunks` and, in **one `BEGIN IMMEDIATE …
COMMIT`** transaction:

- the table exists and `document_count_all(conn) == 0` → `DROP TABLE
  vec_chunks` (the orphan is recovered);
- the table exists and a document exists → `ConfigError("vec_chunks exists
  without a rag.embedding pair while documents exist; delete the documents
  (see README Limitations) before configuring EMBEDDING_MODEL/EMBEDDING_DIM")`,
  raised **without altering anything** — no drop, no create, no write;
- then `CREATE VIRTUAL TABLE vec_chunks` at the **configured** dimension
  (STO-02's DDL) and write `rag.embedding`.

**Creation and state binding never commit separately** — on either path
the table and the pair land together or neither lands.

On every later start with `embedding_dim` set and a stored pair that differs
from `f"{model}:{dim}"`, **exactly one of two things happens**, decided by
`document_count_all(conn)` (STO-05) — the count of every row of `documents`,
across all users — read **before any DDL**:

- **a document exists** → `ConfigError("EMBEDDING_MODEL/EMBEDDING_DIM differ
  from the indexed pair <stored>; delete the documents (see README
  Limitations) before changing them")` is raised **before any DDL runs** and
  no state is altered;
- **`document_count_all(conn) == 0`** → one `BEGIN IMMEDIATE … COMMIT`
  transaction performs the **empty-index rebind**, in this order: `DROP
  TABLE IF EXISTS vec_chunks`, delete the `rag.embedding` key,
  `CREATE VIRTUAL TABLE vec_chunks` with the **configured** dimension
  (STO-02's DDL), write `'<model>:<dim>'`. A model-only change and a
  dimension change are both covered by that one path, and because the table
  is dropped first, `CREATE VIRTUAL TABLE IF NOT EXISTS` can no longer
  silently keep a stale dimension while the stored key claims a new one.

A **matching** pair is idempotent: no drop, no rewrite, no DDL beyond the
`IF NOT EXISTS` creation. The `ConfigError` path is
surfaced by `bot.py`'s three `init_schema` callers (`bot.py:1272`, `:1395`, `:1541`)
pass `embedding_dim=cfg.embedding_dim, embedding_model=cfg.embedding_model`,
and `main` reports the error as it reports any `ConfigError` (exit 1, one
line, redacted). `devtools/bench.py:927`'s call is untouched (`None`). A
start with no embedding config and a stored pair is **allowed** (documents
are simply unreachable until the pair is configured again — CMD-01's
"not configured" reply). README Limitations documents the manual fix: for
each document, `/delete <filename>`; then change the pair; the next start
rebinds the empty index in the one transaction above.
D3's "stored on first index", adapted to the table's lifecycle; flagged in
the handoff.

**REQ-V190-STO-05 (MUST) — the storage API, every statement scoped by
user and parameterised.** `storage.py` gains, in this order after
`add_span` (`:657`):

- `add_document(conn, *, user_id, filename, file_type, created_at,
  size_bytes, text_chars, page_count, chunk_count, sha256) -> int` — the
  new `documents.id`;
- `add_chunks(conn, *, user_id, document_id, chunks: Sequence[tuple[int,
  str, int | None, int, int]]) -> list[int]` — `(chunk_index, text, page,
  char_start, char_end)` rows. It **first verifies ownership** with `SELECT
  1 FROM documents WHERE id = ? AND user_id = ?` and raises when that
  returns nothing. It then issues **one parameterised `INSERT` per chunk**,
  collecting each `cursor.lastrowid` — **not `executemany`**, whose cursor
  exposes no reliable sequence of `lastrowid` values — and returns the ids
  in chunk order;
- `add_vectors(conn, *, user_id, rows: Sequence[tuple[int, bytes]])` —
  **it first verifies that every chunk id belongs to `user_id`**, with the
  user-scoped join `SELECT c.id FROM chunks c JOIN documents d ON d.id =
  c.document_id WHERE c.id IN (?, …) AND d.user_id = ?` over the distinct
  requested ids; the returned set must equal the requested set exactly, and
  otherwise it **raises before a single insert** — without this check a
  caller could file another tenant's `chunks.id` under an arbitrary
  partition key, which `add_chunks`'s own ownership check would have
  refused. Only then does it issue `INSERT INTO vec_chunks (chunk_id,
  user_id, embedding) VALUES (?, ?, ?)` via `executemany`;
- `document_id_for(conn, *, user_id, filename) -> int | None`;
- `list_documents(conn, *, user_id) -> list[sqlite3.Row]` — `WHERE user_id
  = ? ORDER BY created_at, id`;
- `delete_document(conn, *, user_id, document_id) -> bool` — the ids to
  delete come from the **user-scoped** select `SELECT c.id FROM chunks c
  JOIN documents d ON d.id = c.document_id WHERE d.id = ? AND d.user_id = ?`;
  each is then removed with the point delete `DELETE FROM vec_chunks WHERE
  chunk_id = ?` — vec0's documented delete form, a delete by primary key,
  whose ownership is carried by the select that produced the id **in the
  same function** (SEC-01 pins that pairing) — and finally `DELETE FROM
  documents WHERE id = ?
  AND user_id = ?` (chunks cascade, `PRAGMA foreign_keys=ON` at
  `storage.py:276`); returns whether a document row was deleted. It runs
  **inside the caller's transaction** when one is open (`index_document`)
  and opens its own `BEGIN IMMEDIATE … COMMIT` otherwise (`/delete`) — one
  transaction either way, so vectors and rows never diverge;
- `user_chunks(conn, *, user_id) -> list[sqlite3.Row]` — `SELECT c.id,
  c.text, c.page, c.chunk_index, d.filename FROM chunks c JOIN documents d
  ON d.id = c.document_id WHERE d.user_id = ? ORDER BY c.id` (the BM25
  corpus);
- `knn_chunk_ids(conn, *, user_id, vector: bytes, k: int) -> list[tuple[int,
  float]]` — `SELECT chunk_id, distance FROM vec_chunks WHERE embedding
  MATCH ? AND k = ? AND user_id = ? ORDER BY distance` — STO-02's partition
  key makes this the only authorised form;
- `chunks_by_ids(conn, *, user_id, ids: Sequence[int]) -> list[sqlite3.Row]`
  — the hydrating query, `WHERE c.id IN (?, …) AND d.user_id = ?` — the
  **second** user predicate, so a KNN row that somehow crossed users is
  dropped here;
- `document_count(conn, *, user_id) -> int`;
- `document_count_all(conn) -> int` — every row of `documents`, across
  users. It is the **one** statement in this set with no owner predicate,
  it exists solely for STO-04's two start-up checks (the orphan-table
  recovery at first creation and the empty-index rebind), it returns a

Every statement binds `?` parameters; the only interpolation anywhere in the

DDL's dimension (STO-02). `T-V190-SEC-05`'s rule, exactly: **every runtime DML or `SELECT` over
`documents`, `chunks` or `vec_chunks` carries the owner predicate**; schema

**REQ-V190-RET-01 (MUST) — the embeddings client.** `llm/embeddings.py`

**REQ-V190-RET-07 (MUST) — the `Searcher`.** `rag.Passage` is a frozen
dataclass `(chunk_id, filename, page: int | None, chunk_index, text)`.
`rag.Searcher(conn, *, user_id, embedder, llm, cfg, conv_id, resolve_cost)`
exposes `search(query: str) -> SearchResult`, a frozen dataclass with
**five** fields:

```python
SearchResult(
    passages: list[Passage],
    documents_present: bool,
    rerank_attempted: bool,
    rerank_succeeded: bool,
    rerank_failure: str | None,
)
```

**The three rerank fields are the only sound way to prove the reranker
ran.** Counting `llm_calls` rows cannot distinguish a call that was applied
from one that succeeded and was then discarded by a parse failure or a
bookkeeping error, and a log line is not an API. So the contract is
explicit:

- `rerank_attempted` is `True` exactly when step 4's rerank path was
  entered — `cfg.rag_rerank == "on"` **and** ≥ 2 candidates. With reranking
  off, or with fewer than two candidates, all three fields are `False`,
  `False`, `None`.
- `rerank_succeeded` is set `True` **only after the validated order and all
  required bookkeeping have completed** — the reply parsed, every index in
  `1…len(candidates)` and distinct, the reordered list built, and
  `_record_llm_call`, span finalisation and `resolve_cost` all returned. It
  is the **last** assignment on the success path; anything that raises or
  returns `None` before it leaves it `False`.
- `rerank_failure` is `None` on success and a short **redacted** reason
  string otherwise (the same text the step-4 warning carries). It is
  **never rendered to the model** — TOOL-02's envelope and its `passages: n`
  count are built from `passages` alone and are unaffected by all three
  flags (SEC-03's redaction discipline still applies to anything that would
  reach a sink).

The pipeline runs in **this exact
order — hydration precedes reranking**, because `rerank` takes
`list[Passage]` and needs each passage's filename and text:

1. vector retrieval (RET-03) and BM25 retrieval (RET-04), each ≤ 20 ids;
2. RRF fusion (RET-05) down to **at most ten** chunk ids;
3. **hydrate those ten ids** through `chunks_by_ids` (STO-05) and restore
   the RRF order over the returned rows — the database's row order must
   never reorder the candidates;
4. rerank the resulting `list[Passage]` (RET-06) when `cfg.rag_rerank ==
   "on"` and there are ≥ 2 candidates; **any** rerank failure falls back to
   the hydrated RRF order produced in step 3. The fallback boundary is the
   **whole optional operation, not just the model call**: `Searcher.search`
   wraps the `rerank` invocation **and all of its bookkeeping** —
   `agent._record_llm_call`, span finalisation, `resolve_cost`, warning
   formatting, anything else that runs on the rerank path — in one
   `try/except Exception`, and on any exception returns the hydrated RRF
   order of step 3 with `rerank_succeeded=False` and `rerank_failure` set.
   The warning itself is emitted **inside its own guarded
   block** (a redacted, best-effort `log.warning`), so a failing logger or a
   failing call recorder cannot escape into the answer either;
5. slice to the first `cfg.rag_top_k` (default **K = 5**).

There is no second hydration step and no undocumented one:
`chunks_by_ids` is called exactly once per `search`.
`documents_present = document_count(...) > 0`.
The `Searcher` keeps `self.calls: list[SearchResult]` — every call of the
turn, in order — for TOOL-05. `user_id` is bound at construction by
`bot.py` (CMD-01) and is not a parameter of `search`. README Retrieval
explains the metric (cosine), K = 5 (five passage bodies of ≤ 1,000 chars —
TOOL-02's `RAG_PASSAGE_CHARS` — fit the 12,000-char tool envelope with
complete headers and leave the model room), and the 20/20/10/5 funnel
(RPT-05).

**REQ-V190-TOOL-05 (MUST) — attribution has a structural guarantee.**
`rag.attach_sources(reply: str, calls: list[SearchResult]) -> tuple[str,
bool]` runs in `bot.py` after `run_agent_outcome` returns and before
`_send` (`bot.py:805-828`), only when `outcome.failed` is false and the
turn's `Searcher` recorded ≥ 1 call:

- **Passages were returned** (any call with ≥ 1 passage): collect the
  distinct `(filename, page)` pairs across those calls in first-seen order,
  at most **5**. One pure function of `rag.py` does all the rendering —
  `rag._render_sources(pairs) -> str`: group the pairs by filename in first-seen
  filename order, each filename followed by `(page N)` for a single page,
  `(pages N, M, …)` for several in first-seen page order, and nothing at all
  when the page is `NULL`; join the filenames with `, `. The canonical block
  is `\n\nSources: ` + `_render_sources(<all collected pairs>)`.

  **Validation never parses a filename.** A filename may legally contain
  commas, parentheses, colons and the words `page`/`pages` — `a, b (page
  9).pdf` is a valid name — so splitting a source line on those delimiters
  admits several readings of the same text and cannot support the
  invented-source guarantee. Instead the bot **generates** and compares:
  for every **non-empty subset** of the collected pairs, in the defined
  first-seen order and with the grouping above, compute
  `_render_sources(subset)`; a line of the reply beginning `Source:` or
  `Sources:` **survives only when its whole text, stripped of surrounding
  whitespace, equals `Source: ` or `Sources: ` followed by one of those
  renderings**. Nothing is extracted from the line and nothing is matched
  loosely — it is one string equality against a generated set. The
  enumeration is safe by construction: at most 5 pairs means at most
  **31** non-empty subsets, computed once per turn. Either prefix is
  accepted, because TOOL-04's prompt line teaches the model the singular
  `Source:`; the block the bot appends always uses `Sources:`.

  Any `Source:`/`Sources:` line that matches no rendering is **removed**,
  with one `log.warning("stripped an invented source line")`. If **no valid
  source line remains** after that pass, the canonical block
  is appended. A filename appearing elsewhere in prose — *"I read
  policy.pdf"* — **does not** satisfy attribution and does not suppress the
  block. Return `(reply, True)` whenever the reply was changed.
  `T-V190-TOOL-08` (negative) pins the delimiter-hostile case: with the
  returned pair `("a, b (page 9).pdf", 9)`, the exact canonical line
  survives, while a line differing anywhere — an added file, a dropped page,
  reordered entries — is stripped and the canonical block appended.
- **No passage was returned by any call**: if the reply contains a line
  starting with `Source:` or `Sources:`, strip those lines, emit one
  `log.warning("stripped an invented source line")`, and return the rest;
  the reply is the model's "the documents do not cover it" answer.
- Otherwise the reply is untouched.

The appended block counts toward `split_message`'s limit (`bot.py:213`),
never past it. Both paths are tested with `FakeLLM` (T-V190-TOOL-05, -06);
the first path is mutation-guarded (`v190-sources-fallback-dropped`).

**REQ-V190-CMD-02 (MUST) — `get_file` and a streaming binary download.**
`TelegramClient` (`bot.py:97-197`) gains `get_file(file_id: str) -> dict`
(`self.call("getFile", {"file_id": file_id},
read_timeout=DEFAULT_READ_TIMEOUT_S)`, the unwrapped `result` with

`DocumentTooLarge` the moment the buffer would exceed `max_bytes` (the
response is closed; nothing more is read).

**A download timeout is a distinguishable type, and the clause order is
normative.** `httpx.TimeoutException` **subclasses** `httpx.TransportError`,
so a single `except httpx.TransportError` clause would swallow every timeout
into a plain `TelegramError` and ERR-01 row 10a's exact string would be
unreachable. `bot.py` therefore defines
`TelegramDownloadTimeout(TelegramError)` beside `TelegramError`, and
`download_file`'s handlers stand in **this order**:

```python
except httpx.TimeoutException as exc:
    raise TelegramDownloadTimeout("download timed out") from exc
except httpx.TransportError as exc:
    raise TelegramError(...) from exc
```

The timeout clause is **first**; a non-200 status or any other
`TransportError` raises the plain `TelegramError` (ERR-01 row 11), and the
handler catches `TelegramDownloadTimeout` **before** `TelegramError`, so
row 10a is matched **by type** and never by parsing a message. Both messages
are `redact()`-ed as `call` does (`:124-142`); the URL embeds the token and
is never logged, and neither exception text carries it. `T-V190-CMD-10`
(negative) proves this through the **real `download_file` boundary** with an
`httpx.MockTransport` that raises `httpx.ReadTimeout` — not a handler
monkeypatch, which would prove nothing about the clause order. The method
is injected like every seam: the fake of TST-02 implements both.

## 9. Security

**REQ-V190-SEC-01 (MUST) — the user predicate on every runtime statement,
and the partition key on the KNN.** Every runtime DML or `SELECT` STO-05
lists carries `user_id = ?` (or `d.user_id = ?` through the join) and binds
it; the KNN carries the partition key (`AND user_id = ?`) **and** the
hydrating query carries the predicate again. **Both write paths into the
index verify ownership before inserting**: `add_chunks` for its
`document_id`, `add_vectors` for every chunk id it is handed (STO-05) — a
partition key is a filter, not a proof of ownership, so nothing reaches
`vec_chunks` under a `user_id` the chunk does not belong to.
`SELECT … FROM chunks` without
the owner filter — the pattern the assignment names as wrong (R8) — does
not exist in the tree. **Two exemptions, both named and both narrow:**
schema DDL, which names no owner; and the point delete `DELETE FROM
vec_chunks WHERE chunk_id = ?`, permitted **only** inside a function that
also contains STO-05's user-scoped id select, plus `document_count_all`,
which returns a bare count for STO-04's start-up check and never a row.
`T-V190-SEC-05` enforces exactly that rule over `storage.py` and `rag.py`
(AST walk, runtime statements only). Two users with the
**same filename** each see only their own document, in search, in
`/documents` and in `/delete` (T-V190-SEC-01…03); the three read paths and
the delete path are mutation-guarded (EC-10).

**REQ-V190-SEC-02 (MUST) — the model cannot choose the user.** The tool
schema has one property and `additionalProperties: False` (TOOL-01); the
dispatcher ignores every key but `query` (TOOL-02); `user_id` is bound in
`bot.py` from the update's verified sender (`:746`) into the `Searcher`
(CMD-01) and is not a parameter of `search`. T-V190-SEC-04 passes
`{"query": "x", "user_id": 7}` and asserts the searcher was called for the
bound user and the extra key changed nothing.

**REQ-V190-SEC-03 (MUST) — filenames are redacted and capped before any
sink.** `clean_filename` caps at 120 (DOC-01); every message, status line
and log line that carries a filename passes `redact()` (`config.py:161`)
first — the tool envelope through `_envelope` (`tools.py:1351`), the
commands through `_send`'s `redact(part)` (`bot.py:1089`), the status edits
through `_edit`'s `redact(text)` (`:320`). Passages are untrusted data by
the existing prompt rule (`agent.py:122-123`) and the tool result is a
`tool` message, never a system one.

**REQ-V190-SEC-04 (MUST) — no file on disk, no unbounded read.** The
download is capped mid-stream (CMD-02), parsed from `bytes`, and never
written: `documents.py` and the new `bot.py` handler contain no `open(`,
no `Path(`, no `tempfile`, no `write_bytes` (T-V190-SEC-04 greps the
module and the handler's source through `inspect.getsource`). The sandbox
(`EXEC_WORKDIR`) is not involved.

**REQ-V190-SEC-05 (MUST) — deletion is scoped and atomic.** `/delete`
resolves the id through `document_id_for(user_id=from_id, …)` and
`delete_document(user_id=from_id, …)` re-checks it (STO-05); one
transaction removes vectors, chunks and the row together, so a crash
between them cannot leave a vector without a chunk or a chunk without a
document. After deletion the document contributes to no search
(T-V190-STO-03 searches before and after; A12).

sections separated by a line holding only `\f`, rendered at eval time to a
3-page PDF by `devtools/pdf_fixture.py` (DOC-06) — Helvetica, ASCII, so
page-number checks are exact). Facts are **disjoint across files**, so
`expected_source` is unambiguous; the DOCX and PDF bytes are built in memory
at eval and test time, never committed.

**REQ-V190-EVAL-02 (MUST) — the question set.** `evals/rag/questions.json`
is a JSON array of **12** objects `{"question": str, "expected_source": str
| null, "expected_page": int | null, "expected_evidence": str | null}`:
**10 answerable** — at least 2 per source, and the 3 PDF items carry
`expected_page` (1, 2, 3) — and **2** with `expected_source: null` (facts
none of the files contain). **Every answerable item carries a non-empty
`expected_evidence`**: the answer-bearing substring, as it stands in that
source's extracted text — the phrase that makes a passage evidence rather
than merely the right file. It is **immutable** (EVAL-03's freeze); the two
null items carry `null`. Questions are in the language of their source. The
file is validated by `T-V190-EVAL-01` (shape, counts, that every
`expected_source` names a corpus file, that every answerable item has an
`expected_evidence`) and by `T-V190-EVAL-04` (that each one occurs in the
extracted text of its source).

**REQ-V190-EVAL-03 (MUST) — `devtools/rag_eval.py`: three modes, two
metrics, one floor.** `main()` loads `Config` (`load_config`), builds an
`EmbeddingsClient` and the LLM client exactly as `bot.py` does, creates a
temporary database (`tempfile.TemporaryDirectory` — executor tooling, so
EC-01's ephemeral-file permission covers it; the context manager removes the
directory on exit — `storage.connect`,
`init_schema(embedding_dim=…, embedding_model=…)`), indexes the four
corpus documents for **synthetic user id −1** through
`documents.index_document` (the production pipeline, no Telegram; it passes
`started_at=time.monotonic()` per document, DOC-05's required argument, and
`progress=` a no-op sink since it owns no status message), then
for every question and each mode — `vector` (RET-03 alone, top-5),
`hybrid` (RET-03 + RET-04 + RET-05, top-5), `hybrid+rerank` (the full
`Searcher.search`) — records the **first-hit rank**.

**The evaluator does not inherit the deployment's retrieval settings.**
`rag_eval.py` loads `Config` for the endpoints and the model names, then
**overrides `rag_rerank = "on"` and `rag_top_k = 5` regardless of the
environment** — otherwise `RAG_RERANK=off` would let the `hybrid+rerank`
mode silently report RRF, and `RAG_TOP_K ≠ 5` would make the reported
recall@5 measure a different cutoff. The override is recorded in the
printed header so the run's own output proves it.

**Hydration for the two id-level modes, normative.** `vector` and `hybrid`
produce chunk ids, while a hit needs `filename`, `page` and `text`. For
each of those two modes: take the **first five ranked ids**, call
`chunks_by_ids(conn, user_id=-1, ids=…)` **exactly once per mode**, drop
ids the query did not return, and **restore the original ranked-id order**
over the returned rows before any evidence or page scoring — the database's
row order must never become the ranking, and the tenant predicate is never
dropped for the synthetic user. `hybrid+rerank` needs none of this:
`Searcher.search` returns hydrated `Passage`es already.

**A hit is evidence, not a filename.** A passage counts only when its
`filename` equals `expected_source` **and** its text contains
`expected_evidence` (compared case-insensitively over whitespace-normalised
text). The first-hit rank is the 1-based position of the first such passage
in that mode's top-5, or none. The metrics, normative here and **adopted
from the lab's assignment-4 project, not read by this run**, over the ten
answerable items: **recall@5** = hits ÷ answerable; **MRR** =
mean(1 / first-hit rank, counting 0 for an item with no hit); the **page
hit-rate** = the share of the three PDF items whose first hit carries
`page == expected_page`. All three are reported per mode. The two null items are
**advisory**: reported as "no passage from any file" vs "passages
returned", never scored. The conversation-aware smoke (TOOL-06): one live
two-turn exchange through `run_agent_outcome` with the corpus searcher
(turn 1 a question, turn 2 «а в неделях?»); reported `pass` when the second
turn's recorded `search_documents` query contains a token of the first
question, else `fail`; **advisory**, and it spends inference tokens (the
one place in the gate set that does — stated in README Tests).
**The rerank mode must actually run, and the gate cannot pass without it —
proved by the result contract, not by a count or a log.** In a live run the
reranker MUST complete without a **single** fallback on the ten answerable
items, because a bonus mechanism that silently degrades is not evidence
that it works. The evaluator reads RET-07's flags off each answerable item's
`hybrid+rerank` `SearchResult` and **exits 2 unless every one of the ten has
`rerank_attempted is True` and `rerank_succeeded is True`**; the failing
items are named in the exit message together with their `rerank_failure`
strings. Counting `llm_calls` rows is **not** an acceptable substitute — a
successful call whose reply was malformed, or whose bookkeeping raised,
produces a row and no applied rerank — and neither is scraping the warning
log. **Failure to construct or call the chat
model, or failure to obtain one successful rerank for every answerable
item, is an environment failure → exit 2** (round 2 moved this out of exit
1: a reranker that never ran says nothing about retrieval quality, so it is
not a below-floor result). Consequently **the gate can never return 0 while
the rerank mode is reported `n/a`**: `n/a` and exit 0 are mutually
exclusive states of this script. Its recall@5 and MRR are printed
**beside** `hybrid`'s and the report states in one sentence whether the
reranker helped or hurt; there is **no blocking non-regression condition**
on the rerank metrics (Appendix C, R1-8).

**The corpus and the questions freeze at the first live run.** T8 records
`sha256` of every file under `evals/rag/corpus/` and of `questions.json`
**before** the first live run, and repeats both in the report. After that
run those files MUST NOT change in response to a result: a below-floor
score may change **retrieval code or configuration only**. Corpus defects
are caught **offline** instead — `T-V190-EVAL-04` proves, before any live
run, that every `expected_evidence` occurs verbatim in its source's
extracted text.

Output: a Markdown table
(question × mode → `hit@r`/`miss`, then a summary block with recall@5,
MRR, page hit-rate per mode) to stdout. **Exit codes:** 0 when `hybrid`
recall@5 ≥ **0.8** on the answerable items **and** every answerable item's
`SearchResult` carries `rerank_attempted is True and rerank_succeeded is
True`; 1 when `hybrid` recall@5 is below the floor
(the red gate — a retrieval regression); 2 when the environment did not let
the run measure anything it claims to measure — the embeddings endpoint or
the corpus unavailable, the chat model impossible to construct or call, or
**any answerable item whose `rerank_attempted` or `rerank_succeeded` is not
`True`** (each with a `live:
FAIL`-style message naming which item and its `rerank_failure`). The recall floor and the
completed-rerank condition are the only blocking conditions; everything
else is reported into the README table and the report (RPT-02, RPT-05). T-V190-EVAL-02 drives the whole script
offline with `FakeEmbedder` and `FakeLLM` and asserts the metric
arithmetic on a scripted ranking.
