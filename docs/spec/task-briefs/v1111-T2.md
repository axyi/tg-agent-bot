## Executor's mechanisms (spec `:683`, `:687`)

Two test cases the spec names as needing "the executor's mechanism,
recorded in `v1111-T2.md`" -- recorded here, per that instruction:

- **`T-V1111-TAB-01`'s id-12345 document** (spec `:683`): `storage.
  add_document` has no `id=` parameter (it always trusts `cursor.
  lastrowid`), so pinning a specific 5-digit id without inserting 12344
  filler rows means one raw `INSERT` naming `documents.id` explicitly.
  SQLite honours an explicit rowid value on an `INTEGER PRIMARY KEY
  AUTOINCREMENT` column, so this is a plain, synchronous insert -- no
  monkeypatch, no schema change.
- **`T-V1111-TAB-05`'s race (spec `:687`)**: "a caller admitted at 19
  whose 20th document is inserted through `storage` before the worker
  commits" is simulated without a real thread: `_handle_document` is
  driven through `process_update` once (admits at 19 < 20, enqueues the
  job); before `worker.run_one` is called, a 20th document is inserted
  directly via `storage.add_document` (out of band, on the test's own
  thread); only then does `worker.run_one` run to commit, and it now
  finds `document_count == 20`, raising `DocumentLimitExceededError` the
  same way a genuine concurrent second upload would have.
