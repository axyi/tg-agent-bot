# Task brief — v1.9.4 T3: a hung mutation is reported by id, not by the gate's timeout

One commit, prompt 183, after `v194-T2.md` lands.

## The gap (v1.9.2 report "v1.10.0 item"; v1.9.3 closed the tree-safety half)

The only timeout around a mutation run is the gate's own
(`config/quality_gates.yaml` `mutation-all.timeout_seconds`, 1530 s on
v1.9.3). `devtools/mutation_check.py:default_runner` (`:1672-1696`) does
`proc = Popen(...)`, `proc.wait()` with no timeout. If one `pytest`
invocation hangs (a test waiting on a socket, a sandbox container that
never exits), the whole gate runs to 1530 s, `checks.py` SIGTERMs the group,
the runner restores the tree (v1.9.3) — and the output names no mutation:
"timed out after 1530s". The operator cannot tell "one hung" from "the
box was slow".

## Design — the choices are made here

- `default_runner` uses `proc.wait(timeout=_MUTATION_TIMEOUT_S)`; on
  `subprocess.TimeoutExpired`: terminate the child's process group
  (`_terminate_current_child` already exists — reuse it), reap, and return
  a sentinel the caller maps to an outcome.
- **Outcome vocabulary stays `KILLED / SURVIVED / ERRORED / DRIFTED`**
  (`:27-30`): a per-mutation timeout maps to **`ERRORED`**, with the
  message `hung after <N>s (killed)` and the id, so the summary line, the
  exit-code rule at `run_all` (`0 survived, 0 errored, 0 drifted`) and every
  parser of that line are untouched. No fifth outcome.
- `_MUTATION_TIMEOUT_S = 180.0`, module constant, commented with its basis:
  the slowest legitimate single run is the full-suite fallback for a
  survivor (~70 s single-process on this box, measured v1.9.2 T2) plus
  start-up; 180 s is > 2× that and still catches a hang inside the gate's
  budget (1530 s ÷ 180 s ≈ 8 hung mutations before the gate itself trips —
  say that in the comment too).
- The tree is restored by the existing `finally` path in `run_one` exactly
  as for any other outcome — confirm by reading `:1298-1315`, do not add a
  second restore.
