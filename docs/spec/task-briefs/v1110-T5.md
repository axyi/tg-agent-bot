### REQ-V1110-ING-02 — `IngestWorker`: one daemon thread, a bounded queue, its own connection

New `class IngestWorker` in `bot.py`. Constructor signature
`IngestWorker(cfg, tg, embedder, db_path)` (this exact shape is asserted
by `T-V1110-SEC-01`, landed at T6 — get it right now). State:
`queue.Queue(maxsize=INGEST_QUEUE_MAX + 1)` where `INGEST_QUEUE_MAX = 4`
(new module-level constant) — the physical queue has **five** slots,
admission hands out at most **four** job-capacity tokens, one slot always
free for the shutdown sentinel. A **lock-protected in-flight map**
(`from_id -> Reservation | IngestJob`, one `threading.Lock`).

**Two-phase admission API** (all under the lock, atomically):
- `reserve(from_id, filename) -> Reservation | SubmitError`: reserves the
  caller's user slot **and** one capacity token in one atomic step, or
  returns `SubmitError.inflight` (caller already holds a reservation or a
  job) / `SubmitError.full` (no token left) — reserving nothing on
  failure.
- `enqueue(reservation, job) -> None`: swaps the `IngestJob` into the map
  for that reservation and `put_nowait`s it — cannot fail for capacity
  reasons (the token is already the reservation's).
- `release(reservation) -> None`: removes both the user slot and the
  token without enqueueing (used when the status send fails after a
  successful `reserve`).
- `run_one(conn=None) -> None`: one `get()` → process → mark done. **The
  thread wrapper `_run` only loops over `run_one` until shutdown** — keep
  the looping logic out of `run_one` itself, so tests can call `run_one`
  directly, synchronously, once per job.
- `shutdown()`, `close()`, `cancel(from_id) -> bool | None` (`None` no
  job, `True` event set, `False` job is `committing`), `in_flight(from_id)
  -> IngestJob | None` (a bare `Reservation` — the window between
  `reserve` and `enqueue` — counts for `reserve`'s capacity purposes but
  is **not** a job: `in_flight`/`cancel` see `None` for it).

**Connection ownership — read this twice**: `IngestWorker` stores
`db_path`, never a connection, at construction. The **first** `run_one`
that needs a connection calls `storage.connect(db_path)` **on the calling
thread** (production: the daemon thread, called from inside `run_one`'s
`try`, after the job was dequeued — never before), keeps it for every
later job, and `_run`'s `finally` closes it (`close()`, idempotent — safe
to call twice). **No connection acquisition tied to a dequeued job may
happen outside `run_one`'s outermost `finally` boundary**: if
`storage.connect` raises, that job still ends with `DOC_HANDLER_FAILED_REPLY`,
its slot is released, `task_done()` is called, and the worker continues —
the next job tries to acquire again. Production never touches this
connection from the polling thread; the polling thread's own `conn` is
never handed to the worker. For **synchronous tests**: `run_one(conn)`
with a test-supplied connection uses it for that one job and never stores
it; `run_one(conn=None)` acquires the worker-owned one on the calling
(test) thread, and the test closes it via `worker.close()`. No connection
ever crosses threads — a test proves this by monkeypatching
`storage.connect` to record `threading.get_ident()`.

**The document-handler split**: the loop thread's `_handle_document` (or
its successor) keeps `started_at = monotonic()` as its first action and
the **five pre-checks in their existing order**, each still a plain
synchronous reply with no status message and no `getFile` call. Only
**after** the pre-checks does it call `reserve(from_id, filename)`: a
`SubmitError` gets its plain reply (row 6 `inflight` / row 7 `full`, see
ING-03) and nothing else. Only after a **successful** reservation does it
send the status message `📄 received` via `_StatusMessage.update` **from
the loop thread** (so the job carries a live, already-started
`_StatusMessage`) — then `enqueue(reservation, IngestJob(chat_id, from_id,
document, filename, status, started_at, cancel=threading.Event(),
cancel_reason=None, phase="queued"))` and returns. If the status send
raises, call `release(reservation)` instead of enqueueing — nothing
orphaned.

`run_one` dequeues the job **first**, marks it `running` under the lock,
**then** (inside the `try` covered by the outermost `finally`) acquires
the connection, runs the ING-04 checkpoints, `getFile` + `download_file` +
`documents.index_document(..., progress=status.update, cancel=job.cancel,
before_commit=<the committing-phase callable>, budget_s=INDEX_BUDGET_S_DEFAULT)`,
then the success reply or the (moved-verbatim, DOC-03-updated) ERR-01
clause chain. The exception boundary (today's `REQ-V190-CMD-07`, "the loop
survives a handler exception") moves here: any exception ends the job
with `DOC_HANDLER_FAILED_REPLY`, frees the slot (outermost `finally`), and
the worker keeps going.

**Wake-up and shutdown**: `run_one`'s `get()` blocks — that's the wake-up
mechanism, nothing more needed. `shutdown()`: set a stop flag/event, then
**under the lock**, set `cancel_reason = "shutdown"` and the cancel event
on every job in phase `queued` or `running` (never `committing` — it
finishes), then `put_nowait` a **private sentinel object** into the fifth
slot (never handed out by admission, so this `put` cannot raise
`queue.Full` and never blocks behind a running job). `_run` keeps looping
over `run_one`, so it **drains the cancelled jobs ahead of the sentinel**
through the normal outermost `finally` (slot/token release, `task_done()`),
each edited to `❌ Interrupted by restart.` (a failed edit is logged,
never raised). On the sentinel, `_run` calls `task_done()`, exits its
loop, and closes its connection in `finally`. The sentinel consumes no
user slot, no capacity token, and is never counted by `in_flight`.

### REQ-V1110-ING-04 — cooperative cancel; the job phase

Every `IngestJob` carries a lock-protected `phase` (`"queued"` set by
`enqueue`, `"running"` set by `run_one` on dequeue, `"committing"`) and
`cancel_reason: str | None` (`"user"` from `/cancel`, `"shutdown"` from
`shutdown()`, always written under the lock before the event is set).
`/cancel` (add to the dispatch chain) reads the caller's job and phase
**under the lock**: no job → `Nothing to cancel.`; phase `queued` or
`running` → `cancel_reason = "user"`, set the event, reply `Cancelling
<name>…` (plain path); phase `committing` → reply `Indexing is already
finishing.`, **do not** set the event (ERR-01 row 17).

`index_document` gains `cancel: threading.Event | None = None` and
`before_commit: Callable[[], None] | None = None` — the worker's
`before_commit` callable, invoked immediately before `BEGIN IMMEDIATE`,
moves the job to `committing` **under the lock**, so the transition is
atomic with respect to `/cancel`'s read (no checkpoint follows it —
`/cancel` reading `committing` after this point always gets "already
finishing", never a race). `_check_budget` gains the same `cancel`
parameter, checked at every existing checkpoint (after extraction,
between PDF pages, after chunking, after each embeddings batch) — a set
event raises `IndexCancelled`. The worker's own
`_check_cancel_budget(job)` helper (raises `IndexCancelled` when
`job.cancel.is_set()`, `IndexBudgetExceeded` when `monotonic() -
job.started_at > INDEX_BUDGET_S_DEFAULT`) runs before `getFile`, after
`getFile`, right after download, and before/after extraction —
`index_document`'s own internal checkpoints follow from there.

`download_file` gains `should_stop: Callable[[], bool] | None = None` —
checked between streamed chunks; the worker passes `job.should_stop` (true
when cancelled or over-budget); when it returns `True` between chunks,
`download_file` closes the stream and returns `None` — the caller's
post-download `_check_cancel_budget(job)` then raises. The agent's own
fetch/exec paths pass nothing (default `None`, unchanged behavior).

A job **already** cancelled when dequeued edits its status immediately
without any Telegram file call (`❌ Cancelled.` for `"user"`, `❌
Interrupted by restart.` for `"shutdown"`). On `IndexCancelled` raised
mid-run: status → `❌ Cancelled.` (nothing stored — every checkpoint
precedes `BEGIN IMMEDIATE`), the worker maps it via
`_document_error_ending` (message kept, slot freed) — `"user"` →
`❌ Cancelled.`, `"shutdown"` → `❌ Interrupted by restart.`. Once
`committing`, `/cancel` never interrupts — the commit proceeds to the
success reply.
