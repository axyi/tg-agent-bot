## Part 1 — four storage.py read functions (REQ-V180-CONV-02)

All mirror `recent_traces`: parameterized SQL, bounds as parameters,
`sqlite3.Row` results, no formatting.

1. **`conversation_row(conn, conv_id) -> sqlite3.Row | None`** — the
   `conversations` row, or `None`. This is the **existence reader**: it
   tells an empty conversation (row exists, zero messages) from an absent
   one (no row), which the message query below cannot.

2. **`recent_conversations(conn, *, limit) -> list[sqlite3.Row]`** — `id`,
   `tg_user_id`, `created_at`, `active`, `message_count` (`COUNT` over
   `messages`), `last_activity` (`MAX(messages.created_at)`, `NULL` for an
   empty conversation). Ordered `created_at DESC, id DESC`, bounded by
   `limit`. A `LEFT JOIN` from `conversations` to `messages` (so a
   conversation with zero messages still appears with `message_count = 0`
   and `last_activity = NULL`) is the natural shape.

3. **`conversation_messages(conn, conv_id, *, limit, cursor) ->
   tuple[list[sqlite3.Row], tuple[int, int] | None]`** — pages **by turn,
   never by row**. `cursor` is the `(turn_id, id)` of the page's first
   message, or `None` for the first page. Implement **exactly** these
   steps, in order:

   0. **Cursor check** (only when `cursor` is not `None`): `SELECT 1 FROM
      messages WHERE conv_id = ? AND turn_id = ? AND id = ? LIMIT 1` — an
      **exact three-column match**, never a range probe (`>=`). No match →
      raise `ValueError` (the caller, T6, turns this into a 400).

   1. **Turn window**: `SELECT turn_id, COUNT(*) AS n, MIN(id) AS first_id
      FROM messages WHERE conv_id = ? AND (turn_id > ? OR (turn_id = ? AND
      id >= ?)) GROUP BY turn_id ORDER BY turn_id ASC LIMIT ?` — the cursor
      pair bound as parameters (both `turn_id > ?` and the `turn_id = ? AND
      id >= ?` clauses use the cursor's `turn_id`; the `id >= ?` uses the
      cursor's `id`), and the limit bound as **`limit + 1`** (a turn holds
      at least one message, so `limit` turns hold at least `limit` messages
      and the extra turn beyond it is the probe). **With no cursor**, omit
      both cursor clauses entirely (`WHERE conv_id = ? GROUP BY turn_id
      ORDER BY turn_id ASC LIMIT ?`) — the window starts at the
      conversation's first turn.

   2. **The page**: take turns from the window in order while the running
      message count stays `< limit`; the turn that crosses `limit` is
      taken **whole** — so a page is *up to `limit` messages, extended to
      the end of the last turn taken*.

   3. **The probe**: the first turn from the window **not** taken by step
      2. It is **never fetched or rendered** — only its `(turn_id,
      first_id)` pair is kept, for step 5's cursor logic.

   4. **The messages**: `SELECT turn_id, role, content, tool_call_id,
      created_at, id FROM messages WHERE conv_id = ? AND turn_id IN (...)`
      **plus** the same cursor clause as step 1 when a cursor was given (so
      a cursor landing inside a turn resumes at its own message instead of
      repeating the whole turn), `ORDER BY turn_id ASC, id ASC`, one bound
      placeholder per taken turn id. **Bound in SQL** by `LIMIT
      TRANSCRIPT_FETCH_ROWS_MAX + 1` where `TRANSCRIPT_FETCH_ROWS_MAX =
      2000` is a new `storage.py` module constant (four times the maximum
      `limit` of 500, so no lawful page ever reaches it). Hitting this cap
      is **not an error** — the extra row beyond the cap is dropped and its
      turn becomes the split case (this is CONV-04's concern at render
      time, not something you need to implement turn-splitting logic for
      here; your job is just to bound the fetch in SQL and drop what's
      beyond it before returning).

   5. **Return `(rows, next_cursor)`.** `next_cursor` is the `(turn_id,
      id)` of the **first message this reader did not return**: the
      dropped row from step 4's cap if it was hit; otherwise the probe
      turn's `(turn_id, first_id)` from step 3; otherwise `None` (the
      window had no turn beyond what was taken — end of conversation). No
      `has_more` anywhere — its meaning is `next_cursor is not None`.

   A missing conversation (no rows at all for that `conv_id`) yields an
   empty `rows` list and `next_cursor = None` from this function — the
   caller (T6) decides the 404 via `conversation_row`, not by this
   function's empty result (see CONV-03/-07: "A missing conversation
   yields an empty list from the message query and `None` from
   `conversation_row`; the caller decides the 404.").

4. **`conversation_turn_traces(conn, conv_id, turn_ids) -> dict[int, str]`**
   — a mapping `turn_id -> trace_id`, **bounded to exactly the given
   `turn_ids`** (the page's own turn ids, nothing wider — REQ-V180-CONV-05
   item on bounding). Per turn id: the `trace_id` of the **lowest `id` in
   `llm_calls`** for that `(conv_id, turn_id)` whose `trace_id` is
   non-null; if none, the **lowest `id` in `tool_calls`** under the same
   condition; if still none, the turn is **absent from the returned
   mapping** (no key, not `None` as a value). A `UNION`/subquery per source
   table with `MIN(id)` grouped by `turn_id`, filtered `WHERE trace_id IS
   NOT NULL AND conv_id = ? AND turn_id IN (...)`, is a reasonable shape —
   your choice, tests decide correctness.

## Part 2 — two dashboard_render.py builders

5. **`conversation_list_section(rows: Sequence[Any]) -> str`** — one row
   per conversation. Column spec, **declared**, exactly six columns in
   this order: **id** (num, linking to `/conversations/<id>`), **user**
   (num, `tg_user_id`), **started** (num, `created_at`), **messages** (num,
   count), **active** (**text** — `yes`/`no`, ok colour class for `yes`),
   **last activity** (num, `last_activity` or `—` when `NULL` — the
   placeholder keeps the `num` class per T4's `_td_cell` convention, no
   special-casing needed since `_td_cell`/`_th_cell` decide the class from
   `kind` alone). An empty `rows` sequence renders **one empty-state row**,
   never a blank table (mirror `usage_section`'s `colspan` empty-state
   pattern). The page copy line — *"A conversation is one `/new`-to-`/new`
   stretch of chat; this is the list of them."* — is **not** this
   function's job unless you judge it belongs in the section fragment
   itself rather than the page-level body T6 assembles; either placement
   is fine, note which you chose in your report.

6. **`conversation_transcript_section(messages, *, chrome_bytes: int,
   budget_bytes: int = TRANSCRIPT_PAGE_BUDGET_BYTES, suffix_bytes: int =
   TRANSCRIPT_PAGE_SUFFIX_BYTES) -> tuple[str, tuple[int,int] | None,
   bool]`** (signature is a suggestion — get the semantics right, the exact
   parameter/return shape is yours to decide, document it clearly). Two
   new module constants: `TRANSCRIPT_PAGE_BUDGET_BYTES = 1_572_864` (1.5
   MiB), `TRANSCRIPT_PAGE_SUFFIX_BYTES = 4096`.

   **Critical purity note**: this function must stay pure (no I/O, no
   `Path`), so it cannot itself measure `page()`'s actual chrome bytes
   (nav/style/headings) — that's the caller's (T6's) job, rendering the
   shell once and measuring `len(...encode("utf-8"))`, then passing the
   result in as `chrome_bytes`. This function seeds its own accumulator
   with `chrome_bytes + suffix_bytes` before admitting any row — this is
   what makes the budget bound the *whole response*, not just the rows.

   **Input assumption**: `messages` arrive **already redacted and
   truncated** to 2000 characters of redacted plain text per message
   (that happens upstream, in `dashboard_server.py`/T6, which can import
   `config` — this module still cannot). Your job here is **only**:
   escaping (`esc()`) and the **atomic turn admission** below, measured on
   **rendered bytes** (i.e. UTF-8-encoded length of the HTML this function
   itself produces per turn).

   **Atomic turn admission**, per turn, in this exact order:
   1. Render the whole turn's HTML and measure its UTF-8 byte length.
   2. It fits the remaining budget → admit the **entire** turn.
   3. It does not fit and the page **already holds a turn** → stop; the
      next cursor is that turn's first message's `(turn_id, id)`.
   4. It does not fit and the page is **empty** → **split** it: render at
      least one message (so the page always advances even for one
      pathologically large turn), mark it **continued**. This is the
      **only** case a turn is ever split — `limit` alone never splits one
      (that's `conversation_messages`'s job), and no turn is split merely
      for missing the space left in a part-filled page.

   The returned **next cursor is the `(turn_id, id)` of the first message
   this render did not include** — which may differ from
   `conversation_messages`'s own `next_cursor` when the byte budget (not
   the turn window) is what stopped the page early. Design the function so
   the caller can tell the two apart or reconcile them — your choice how,
   but the **page's own emitted next-link must reflect what was actually
   rendered**, never `conversation_messages`'s reader-level cursor when the
   two disagree.

   Per-message rendering: role (visible as text, not colour alone), turn
   id and timestamp are the rail's **num** fields, role/trace-link/content
   are **not**. A `tool` row also shows its `tool_call_id`. The trace link
   (when the turn has one — via `conversation_turn_traces`, which the
   caller looks up and hands you, or a parameter you accept for it — your
   choice of exact signature) is plain text with **no arrow appended**
   when absent, or `<a href="/traces/{trace_id}">{abbreviated}</a>` when
   present. No `has_more` key or field anywhere in this module — that
   concept doesn't exist here (`next_cursor is not None` is the whole
   meaning).
