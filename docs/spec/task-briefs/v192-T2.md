## 2. Gate 6 — the headline lever: test *ordering*, not test selection

`devtools/mutation_check.py:default_runner` runs `uv run --locked pytest -x -q
--deselect <self-check>` with `PYTHONDONTWRITEBYTECODE=1`. With `-x`, a kill
costs the time until the first failing test; pytest's default order is
alphabetical by file, so a `rag.py` mutation runs ~1400 tests before
`tests/test_v190_retrieval.py` fails. 108 entries × avg 34 s = 61m39s.

Measured with a scratch runner (mutate → `pytest -x -q <files in order>` →
restore; `/home/akh/.claude/jobs/45feeee3/tmp/t2/sim_order.py`):

| entry | default order | importers-first |
|---|---|---|
| `v191-rerank-retry-dropped` (rag.py) | 72.5 s killed | **2.3 s** killed |
| `v160-readonly-connection-writable` (storage.py, imported by 30 test files) | 58.1 s killed | **16.0 s** killed |

Overheads that bound the floor: `pytest --collect-only -q` 1.35 s;
`uv run python -c pass` 0.03 s; bytecode cache on/off made no measurable
difference on a one-file run (1.02 vs 1.10 s) — keep
`PYTHONDONTWRITEBYTECODE=1` as is.

### 2.1 Design — no test is ever excluded, only reordered

`default_runner(mutation)` builds an **explicit, complete, ordered list of
every test file** and passes it as pytest args. Tiers, first to last, stable
sort within a tier:

1. test files whose name carries the entry's version prefix
   (`v160-…` → `tests/test_v160_*.py`; `cov-…` → `tests/test_v12_patch.py`,
   the only file naming `cov_0*` ids — verify by grep; a prefix with no
   matching file simply contributes nothing to this tier);
2. the test file named after the mutated module (`storage.py` →
   `tests/test_storage.py`, `llm/failover.py` → `tests/test_failover.py`);
3. test files that import the mutated module directly (`^(from|import)
   <module>` on the file text);
4. test files importing a first-party module that imports it (one hop);
5. every remaining test file.

Two facts from the collection probe on pytest 9.1.1 that the implementation
must respect:

- `pytest tests/test_x.py tests/` **does not** put `test_x.py` first — pytest
  dedups and keeps the directory's order (the explicit file landed at
  position 1435 of 1593). Only an explicit list of *files* orders the run;
  `pytest a.py b.py c.py` collects in argv order (verified: 160 tests, argv
  order kept).
- **Silent-shrink hazard.** An explicit file list is a new way to lose tests:
  a future `tests/sub/test_x.py` or a renamed pattern would drop out of the
  mutation gate while the gate still reports green over a smaller set — the
  hole REQ-V13-CO-06 / REQ-V15-GATE-04 exist to close. The runner MUST
  check, **once per invocation** (not per mutation): `pytest --collect-only
  -q <ordered list>` collects the same node count as `pytest --collect-only
  -q` (no args; `testpaths` from `pyproject.toml`), and fail loudly with
  both counts if not. Add a mutation entry `v192-mutation-order-shrink-
  unchecked` that removes the check, and a unit test that kills it (fake the
  two counts).

The ordering is a pure performance property: the killed set is identical by
construction. Prove that once, before trusting the first fast 108/108:

- **False-kill guard.** With `-x` a reordered run could "kill" via a test
  that fails for an ordering reason. Run the **unmutated** tree once under
  each distinct ordering the runner produces (one per distinct mutated
  path — about a dozen, ~70 s each, nothing else running). All green ⇒ every
  kill is attributable. Put the list of orderings and the 12 exit codes in
  the report.
- xdist and this do **not** compose: worker start-up (~2–3 s) would make the
  2.3 s case slower. The mutation runner stays single-process — pass `-p
  no:xdist` or `-n 0` explicitly if §3 puts xdist in `addopts`.

Then measure: `time uv run --locked python devtools/mutation_check.py
--select v15-` / `v160-` / `v170-` / `v180-` / `v190-`, each alone, nothing
concurrent, and put before/after in the report. The full `mutation-all` run
is T3's; do not run it here.

## 3. Gate 3 — pytest wall clock

### 3.1 Fixture cost, free (~10 s)

`live_server` fixtures (`tests/test_v160_dashboard.py:705`, `:859`;
`tests/test_v180_conversations.py:479`) run `server.serve_forever()` at the
default `poll_interval=0.5`, so each `shutdown()` waits up to half a second —
that is the wall of `0.50s teardown` rows. `serve_forever(poll_interval=
0.01)` in the thread target; fixture-only, no property under test changes.

### 3.2 `test_exec` grace periods (~8 s), with one guard

`test_t_ex_04` = `timeout_s=1.0` + `EXEC_KILL_GRACE_S=5.0`; `test_t_ex_05`
adds `EXEC_DRAIN_GRACE_S=2.0` twice. Monkeypatch the constants down (0.5 /
0.2) in those tests **and scale their `elapsed <` bounds with the patched
value**, but keep exactly one test at the production grace so the real
constant is still exercised — say which one in the report.

### 3.3 xdist (measured, green)

## 4. Duplicates and redundancy — the honest answer

Scan, cheaply: (a) the same REQ id asserted in two tests with the same
assertions; (b) test bodies differing only in a literal that should be one
`@pytest.mark.parametrize`; (c) the top-50 list above — is any slow test
covered by a faster one? For each candidate: name the covering test, then
prove it with `mutation_check.py --only <entry>` for every entry whose `find`
lives in the module the candidate exercises, before and after. Remove only
with proof; record `removed <test> — covered by <test>, mutation <entry>
still killed`. Parametrize merges are not removals and need no proof beyond
green. The report says plainly: "N candidates, X removed with proof, Y
merged, the suite's time is in §1's ten tests, not in duplicates."
