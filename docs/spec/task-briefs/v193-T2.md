## The evidence, verbatim

Every clean gate-7 run since v1.9.1 T3 shows the same three lines at the
very top of the log, before anything else is printed:

```
rerank attempt 1 failed, retrying: llm request timed out
rerank attempt 2 failed, retrying: llm request timed out
rerank succeeded on attempt 3 after 15.72s        (v1.9.2 T3; v1.9.1: 15.84s)
```

Facts that bound the diagnosis (`rag.py:254-272`, `llm/base.py:395-400`):

- `_RERANK_TIMEOUT_S = 15.0` is passed straight to `httpx` as
  `client.post(..., timeout=15.0)` — a **per-phase** timeout (connect,
  write, read, pool). For a non-streaming completion, "read" ≈ time to
  first byte ≈ the upstream's whole generation time. A call that completes
  in 15.72 s total under a 15.0 s read timeout therefore had TTFB ≤ 15 s
  plus connect/overhead — it is genuinely sitting **at** the ceiling.
- `elapsed_s` (`:256`, `:272`) is per attempt and wraps only
  `llm.complete`; the span and payload work inside it are milliseconds.
  So 15.72 s is the HTTP call, not our overhead.
- The other nine items' rerank calls take 1–2 s (v1.9.1 measurements,
  `docs/spec/task-briefs/v191-T1.md`). One item is ~10× slower, every run.
- The three lines are the **first** thing logged in every run. Two
  hypotheses fit: (H1) it is always the first rerank call of the process
  — cold start (TLS, provider routing, upstream warm-up) — and the item is
  incidental; (H2) it is one specific item whose candidate set makes the
  model slow (long generation up to `_RERANK_MAX_TOKENS = 128`, or an
  upstream that routes that request badly).

## Fix — one of these, chosen by the probe; the report says which and why

- **H1 (cold start):** a warm-up is the fix, not a timeout. Add a
  `warm_up()` on the rerank route: one minimal completion
  (`max_tokens=1`, a two-line message) issued once per process the first
  time `rerank()` is entered, its failure ignored and logged at debug; or,
  cheaper and with no extra call, give **attempt 1 only** a longer timeout
  (`_RERANK_FIRST_ATTEMPT_TIMEOUT_S`, measured from the probe's cold TTFB
  plus 2× headroom). Prefer the per-attempt timeout unless the probe shows
  cold TTFB above ~25 s. Either way the worst case per item
  (`_RERANK_TIMEOUT_S` × attempts + backoff, or first + 2 × normal + backoff)
  is written next to the constant, and `rag-eval`'s gate timeout
  (`config/quality_gates.yaml:210`, 580 s) is checked against 10 items ×
  worst case and against 2× the measured wall — the file's own rule wins.
- **H2 (item-bound, long generation):** look at `completion_tokens`. If the
  model emits near 128 tokens for that item, the JSON schema is being
  padded (e.g. the model writes whitespace or repeats) — inspect the raw
  content; the fix is on the prompt/schema side (`_RERANK_SYSTEM`,
  `_rerank_response_format`) and must be re-measured on all ten items for
  recall (v1.9.1's quality table is the bar: recall@5 ≥ 9/10 with schema).
  If tokens are small and the time is upstream, pin the provider
  (`provider: {"order": [...]}` in the payload — `llm/openrouter.py`
  carries no `provider` block today; adding one is a payload change
  guarded by the same `_PROTECTED_PAYLOAD_KEYS` pattern) or raise
  `_RERANK_TIMEOUT_S` to 2× the measured slow TTFB, whichever the probe
  supports — say why.
- **In every case:** the fix is proven by **three consecutive clean gate-7
  runs** (`uv run --locked python devtools/rag_eval.py`, alone, nothing
  else on the box, never concurrent with a mutation run) whose logs show
  **zero** `rerank attempt … failed` lines, walls recorded; plus a unit
  test at the layer the fix lives in (a per-attempt timeout → assert the
  fake client received the first-attempt value then the normal one; a
  warm-up → assert exactly one warm-up call per process and that its
  failure does not propagate) and one `v193-rerank-…` mutation entry killed
  by it. `rag.py` find strings: keep drift 0; re-derive any the edit moves
  and `--only` them.
