## `index_document` (DOC-05) — signature and stages

```python
def index_document(
    conn, *, user_id: int, filename: str, data: bytes, embedder,
    progress: Callable[[str], None], now: str, started_at: float,
    monotonic=time.monotonic, budget_s: float = 300.0,
) -> IndexResult
```

`IndexResult(chunk_count: int, page_count: int | None, text_chars: int,
replaced: bool)`. `started_at` has **no default** — the caller (T7) must
supply it; it is `monotonic()` read as the handler's **first action**,
before `getFile`, before download, before the status message (DOC-04) —
T4 does not capture it itself, only consumes it.

Stages, in order: classify → extract → chunk → embed (batches of 32
through `embedder.embed`) → store. `index_document` emits **only three**
progress strings, exactly: `"📄 extracted: …"` after extraction,
`"📄 chunked: N"` after chunking, `"📄 embedding: i/n"` after each
embeddings batch. **Classify and store emit nothing** — do not add a
fourth or fifth progress call. `index_document` never touches Telegram —
`progress` is its only output channel besides the return value and
exceptions.

## Limits and the budget (DOC-04), checked in this exact order

After extraction: (1) extracted text over **500,000** characters (summed
over all pages) → raise a named "too large (text)" exception; (2) fewer
than **20** non-whitespace characters → raise a named "empty" exception;
(3) the wall-clock budget, **300 s default**, checked **between stages**
(after extraction, after chunking, after every embeddings batch) via
`monotonic() - started_at > budget_s` → raise `documents.IndexBudgetExceeded`
(already partially wired by T3 inside the PDF per-page loop — **your job is
to thread the same check between every other stage boundary too**, and to
make sure `IndexBudgetExceeded` raised inside PDF extraction propagates
un-mapped, never caught by a corruption handler). On any of these: **raise
before any store, nothing is written** — no transaction has opened yet.

**The 20-document limit, re-checked.** `index_document` re-checks "user
already has 20 documents and this filename is not one of them" **inside
the indexing transaction, immediately before the document row is
inserted** — this is the transactional half of ERR-01 row 13 (the
pre-check before the status message is T7's, a separate call site; both
map to the **same** row-13 string family, but you only implement the
in-transaction one). Raise the same named exception T7 will need to
recognise (pick one name and document it in your report — T7's brief will
be told what you chose).

## The transaction, and what it does not cover

One transaction (`BEGIN IMMEDIATE` … `COMMIT`), opened **only after the
last embeddings batch has returned** — so a failure at any earlier stage
leaves the database untouched, including the replaced document on a
re-upload. Inside it, in order: the 20-document recheck above; if a row
`documents(user_id, filename)` already exists, delete it first via
`storage.delete_document` (vectors, chunks, row — same transaction); insert
the new `documents` row (`size_bytes = len(data)`, `sha256 =
hashlib.sha256(data).hexdigest()`, `page_count` = count of non-empty PDF
pages or `NULL` for other types, `chunk_count`, `text_chars`, `created_at =
now`); insert its chunks via `storage.add_chunks`; insert one `vec_chunks`
row per chunk via `storage.add_vectors`, keyed by each chunk's id and
`user_id`. `replaced=True` iff a row was deleted. No versioning.

**No `rag.embedding` or `vec_chunks` lifecycle statement exists anywhere in
`index_document`** — that lives exclusively in `init_schema` under STO-04
(T1's job, already done). If you find yourself wanting to touch
`rag.embedding` or create/drop `vec_chunks` here, stop — that is a sign
something is structured wrong.

**What the budget is not.** A single library call inside a stage is not
interruptible — no cancellable worker. The hard bounds on a stage come
from the size guards (10 MiB download cap — T7's job; the DOCX/PDF guards
— T3's, already done), not from the wall clock alone.
