# Task brief — v1.9.1 T1: make the rerank contract enforceable and fast

Patch release, no new spec file (precedent: v1.5.1, "патч, без новой спеки" in
the lab ledger). This brief is the contract. Everything load-bearing is here;
do not re-derive it from the conversation that produced it.

## Why this patch exists

Gate 7 (`devtools/rag_eval.py`) has been red since v1.9.0 T8 and was shipped
under an operator waiver. `/verify-run` reproduced it independently on
2026-09-12. The cause is now **measured, not inferred**:

| Configuration | parsed | recall@5 | median s/call | completion tokens |
|---|---|---|---|---|
| `qwen/qwen3.8-27b`, 2048 tok, no schema (**production today**) | 5/5 | 5/5 | **196.9** | 695–1152 |
| `qwen/qwen3.8-27b`, 64 tok, JSON schema | 0/10 | — | 16.4 | 35, empty content |
| `google/gemma-4-e4b`, 2048 tok, no schema | 10/10 | 9/10 | 35.9 | 132–688 |
| `google/gemma-4-e4b`, 512 tok, JSON schema | 4/10 | — | 34.9 | 6 of 10 hit the cap |
| `google/gemma-4-12b-qat`, 64 tok, JSON schema | 0/10 | — | 8.5 | 64, capped |
| **`google/gemma-3-12b-it` via OpenRouter, 64 tok, schema** | **10/10** | **10/10** | **0.83** | 10–53 |
| `mistralai/mistral-nemo` via OpenRouter, 64 tok, schema | 10/10 | 9/10 | 1.61 | 10–35 |
| `mistralai/mistral-nemo` via OpenRouter, 64 tok, **no** schema | 9/10 | **6/10** | 0.96 | 4–7 |

Measured with a verbatim port of `_RERANK_SYSTEM`, `_rerank_messages` and
`_parse_rerank_reply` against the real `evals/rag/corpus`, with the gold
passage planted outside the top-5 so reranking has to do real work.

Three facts follow, and they are the whole design:

1. **`_RERANK_TIMEOUT_S` is 120.0 and the production model's median is 196.9 s.**
   Most rerank calls cannot finish. Gate 7 was never flaky — it was structurally
   impossible. 10 answerable items x 196.9 s ~ 1970 s against
   `config/quality_gates.yaml`'s `rag-eval` `timeout_seconds: 600`.
2. **Every chat model on the GPU box is a thinking model**, the `gemma-4` family
   included — `gemma-4-e4b` and `gemma-4-12b-qat` burn the entire completion
   budget on reasoning and return *empty content* at 64 and (6 times in 10) at
   512 tokens. There is no local non-thinking chat model to switch to. The box
   holds only `text-embedding-nomic-embed-text-v1.5` as a non-chat model.
3. **A JSON schema is not cosmetic — it carries half the quality.** Without it
   `mistral-nemo` replies with two-element arrays (4–7 completion tokens) that
   parse fine but leave eight of ten candidates in RRF order: recall@5 falls
   9/10 -> 6/10. With it, the model returns a real ordering.

The observed maximum completion length across every passing configuration is
**53 tokens**. `_RERANK_MAX_TOKENS = 2048` exists only to absorb another
model's chain-of-thought (`rag.py:40-48` says so itself).

## What to change

### 1. `response_format` passthrough — `llm/base.py`

`build_payload` (`llm/base.py:228-235`) gains a keyword-only
`response_format: dict | None = None`, merged into the payload like
`reasoning_fields` already is, and subject to the same
`_PROTECTED_PAYLOAD_KEYS` collision guard (`llm/base.py:246-250`) — a caller
must not be able to overwrite a protected key through it. Thread it through
`LLMClient.complete` (`llm/base.py:176`), `llm/lmstudio.py:38`,
`llm/openrouter.py:74` and `llm/failover.py:58`. Default `None` everywhere:
no existing call site changes shape.

### 2. The rerank call asks for a schema — `rag.py`

`rag.py:201`'s neighbourhood, where the rerank completion is issued. Send:

```json
{"type": "json_schema",
 "json_schema": {"name": "rerank", "strict": true,
   "schema": {"type": "object",
     "properties": {"order": {"type": "array",
        "items": {"type": "integer", "minimum": 1, "maximum": <n>},
        "minItems": 1, "maxItems": <n>}},
     "required": ["order"], "additionalProperties": false}}}
```

`<n>` is the candidate count actually sent, not the `_HYBRID_CANDIDATES`
constant. **`_parse_rerank_reply` needs no change**: its
`re.search(r"\[.*?\]", ...)` already lifts the array out of
`{"order": [6, 7]}` — verified against live replies from all four routed
models. Do not "improve" the parser in this patch; add a test that pins the
`{"order": [...]}` shape so the behaviour is deliberate rather than incidental.

### 3. Budgets come back to earth — `rag.py`

- `_RERANK_MAX_TOKENS` (`rag.py:49`): 2048 -> **128** (measured max 53).
- `_RERANK_TIMEOUT_S` (`rag.py:61`): 120.0 -> **30.0** (measured median 0.83 s
  on the routed model; 30 s absorbs a provider hiccup and still fails fast).

Rewrite the two long comments above them (`rag.py:40-48`, `rag.py:50-60`).
They currently narrate the thinking-model workaround as if it were the final
word; replace them with the measured reason for the new values and a pointer
to `docs/reports/report-v1.9.1.md`. Keep them honest: state that a thinking
model pointed at rerank will now truncate and fall back to RRF order, which is
a safe degradation the gate catches, not a silent one.

### 4. `LLM_RERANK_MODEL` — `config.py`, `llm/__init__.py`

Exactly the shape `LLM_SUMMARY_MODEL` already has (`config.py:213-227`,
`llm/__init__.py:43-48`), because that is this repo's established convention
for per-purpose routing and a second convention would be worse than none:

- `LLM_RERANK_MODEL`, format `"<provider>:<model>"`, unset by default.
- Generalise `parse_summary_model` rather than copying it — one parser, two
  call sites — but keep `LLM_SUMMARY_MODEL`'s error text and behaviour
  byte-identical; its existing tests must pass untouched.
- `build_llm_client(..., purpose="rerank")` routes to the named provider with
  no failover, mirroring the `"summary"` branch. Unset -> falls through to the
  main client, so behaviour without configuration is exactly today's.
- Wire the rerank client in at the two `Searcher` construction sites:
  `bot.py:919` and `devtools/rag_eval.py:555`.

Default stays unset — no behaviour change for an unconfigured clone. The
recommended value ships in `.env.example`:
`LLM_RERANK_MODEL=openrouter:google/gemma-3-12b-it`.

### 5. Gate 7's own timeout — `config/quality_gates.yaml`

`rag-eval`'s `timeout_seconds` is 600 (`config/quality_gates.yaml:159`) while
the rerank stage alone could need 1970 s. After this patch, measure one real
green gate-7 run and set `timeout_seconds` to **2x the measured wall clock**,
per the rule this file already follows. Record both numbers in the report.

### 6. Documentation

`.env.example` and README's `## Documents (RAG)` section gain `LLM_RERANK_MODEL`:
what it is, the `"<provider>:<model>"` form, the recommended value, and the
one-line reason (the local box has no non-thinking chat model). AGENTS.md's
Gates section: gate 7 is no longer described as a standing known limitation.

### 7. Tests

Follow the repo's own naming and the test-independence rules in
`standards/workflow.md` §4 — assert values from this brief, never re-derived
from the implementation:

- `build_payload` carries `response_format` when given, omits the key when not,
  and refuses a protected-key collision.
- The rerank request actually carries the schema, with `maximum`/`maxItems`
  equal to the candidate count sent (not the constant).
- `_parse_rerank_reply` accepts `{"order": [3, 1, 2]}` and still accepts a bare
  `[3, 1, 2]`.
- `LLM_RERANK_MODEL` set -> `purpose="rerank"` gets a bare client on the named
  provider with no failover; unset -> the main client; malformed -> `ConfigError`
  with the same wording shape as `LLM_SUMMARY_MODEL`'s.
- `LLM_SUMMARY_MODEL`'s existing behaviour is unchanged (regression guard for
  the parser generalisation).
- The two new constants are pinned to 128 and 30.0 with the measured
  justification in the test's docstring.

Add **two mutation entries** to `devtools/mutation_check.py`, prefix `v191-`:
one that drops `response_format` from the rerank payload, one that makes
`build_llm_client` ignore `LLM_RERANK_MODEL`. Both must be killed. These are
the exact regressions that would silently restore the v1.9.0 bug.
