## What to build

### REQ-V1110-EXT-01 — one command table, registered at startup

`bot.py` gains a module-level `COMMANDS: tuple[tuple[str, str], ...]` —
`(name, description)` pairs, names **without** the leading slash, ≤32
characters, descriptions ≤256 characters, ASCII — for every dispatched
command **except** `/start` (it's the documented alias, not registered),
in this exact order (matches the README table's order):
`new, status, stats, summary, model, reload_skills, documents, delete,
sessions, session, cancel, help`.

New `TelegramClient.set_my_commands(commands: list[dict]) -> bool`:
posts `setMyCommands` with `{"commands": [{"command": …, "description":
…}, …]}`, through `_call_with_retry` like the other methods. `main()`
calls it **once, immediately after `get_me()`** (see the location above);
a `TelegramError` or any exception there is logged
(`log.warning("setMyCommands failed: %s", redact(...))`) and is **never
fatal** — startup continues either way. Neither `run_selftest` nor
`run_selftest_live` calls it.

**Completeness, worth its own care**: every dispatched command except
`/start` appears exactly once in `COMMANDS`; every `COMMANDS` entry is
actually dispatched (a probe update per name reaches its handler, not the
model) — this is the kind of thing that silently rots as commands get
added across releases, so make the test genuinely exercise dispatch, not
just check the tuple's contents against a hardcoded list.

### REQ-V1110-EXT-02 — `/help` and `/start`

Both dispatch to a new `_handle_help` handler, which sends **one
table-path body**: `render_table(("command", "what it does"), COMMANDS,
max_width=(16, 52))` (16+52=68, plus one two-space separator = 70 ≤72
units — via T1's `send_pre`). Neither `/help` nor `/start` is stored in
the conversation (commands never are). Unknown `/…` text still falls
through to the model, unchanged.
