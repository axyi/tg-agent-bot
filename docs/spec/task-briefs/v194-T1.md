## The defect (v1.9.3 report, "Open tail"; T1+T2 review finding 8)

Redaction is call-site-only: `config.redact()` (`config.py:196-201`) is
called at ~105 sites by hand, and there is **no logging-layer filter**. At
the 11 `log.exception(...)` sites the traceback and any chained
`__cause__`/`__context__` are rendered by the `Formatter` from
`record.exc_info` and never pass through `redact()`. The reviewer checked
every site: no registered secret reaches those exception objects **today**.
That is a guarantee by inspection, not by mechanism. This task makes it a
mechanism.

## Design — where the seam is, and why

Four independent logging entry points exist and one of them strips root
handlers:

- `bot.py:1966` `logging.basicConfig(...)` — the bot process;
- `devtools/bench.py:2484-2494` `_configure_logging` — **removes every root
  handler** and adds its own `FileHandler`, so anything attached in a
  `basicConfig` call is gone here;
- `dashboard_server.py:35` and `devtools/rag_eval.py` get loggers with no
  config of their own (they inherit whichever process configured root).

So the seam is a helper every entry point calls, not a filter dropped into
one `basicConfig`. Implement in `config.py`:

- `class RedactingFormatter(logging.Formatter)`: `format()` renders through
  the base class, then returns `redact(rendered)`. Because
  `Formatter.format` renders the message, `exc_info` (`formatException`)
  and `stack_info` into one string, redacting the **rendered** line covers
  the message, its args, the traceback and every chained exception in one
  place. Do not implement this as a `logging.Filter` that rewrites
  `record.msg` — a filter runs before the traceback is rendered and misses
  exactly the text this task is about. Set `record.exc_text = None` after
  formatting if you cache anything, or simply never touch the record.
- `def install_redacting_logging(handler: logging.Handler, fmt: str,
  datefmt: str | None = None) -> None` (or an equivalent that returns the
  formatter) — the one call every entry point makes.

Apply at all four sites: `bot.py` (`basicConfig` → build the handler and
formatter explicitly, same format string and stream), `devtools/bench.py`
(`_configure_logging` uses the redacting formatter on its `FileHandler`),
and for `dashboard_server.py` / `devtools/rag_eval.py` state in the report
which process configures their root logger (the bot for the dashboard
thread; `rag_eval` has no config → records go to `lastResort` stderr — give
`rag_eval.main()` a `basicConfig`-equivalent through the helper so gate 7's
own warnings are redacted too).

**Keep every existing `redact()` call.** Removing them is a large diff with
mutation-`find` fallout, and defence in depth is the intended end state.
Say so in the report.

## Tests — the deliverable is the test, the mechanism is negotiable

In `tests/test_config.py` (or a new `tests/test_v194_redaction.py`), with
`caplog` **not** used for the assertion (caplog captures records before the
formatter — assert on the *emitted text* via a `StringIO` handler carrying
the redacting formatter):

1. a registered secret in the message args → masked in the emitted line;
2. a registered secret inside `str(exc)` of an exception logged with
   `log.exception` → masked in the traceback text;
3. a registered secret inside a chained `__cause__` (`raise X from Y`
   where `str(Y)` carries the secret) → masked;
4. a secret registered **after** the formatter was installed → still masked
   (the formatter reads the live registry at format time, not a snapshot);
5. per entry point: `bot.main`'s logging setup, `bench._configure_logging`
   and `rag_eval.main`'s setup each yield a root handler whose formatter is
   the redacting one (assert on the handler's formatter type).
