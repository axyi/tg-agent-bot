## Vector search (REQ-V190-RET-03)

`rag.vector_search(conn, *, user_id, embedder, query, k=20) -> list[int]`:
embed the query (one text, via `EmbeddingsClient.embed`), then
`storage.knn_chunk_ids(conn, user_id=user_id, vector=<serialized>, k=k)`
(T1's API — check its exact parameter names/serialization expectation,
e.g. `sqlite_vec.serialize_float32`), return chunk ids ordered by
ascending cosine distance. No `vec_chunks` rows for the user → `[]`.

## BM25 over the user's chunks, rebuilt per query (REQ-V190-RET-04)

`rag.tokenize(text) -> list[str]` is, **exactly**:
`snowballstemmer.stemmer("russian").stemWords(re.findall(r"\w+",
text.lower()))` — tokenize with `\w+` over the lowercased text, then run
the Russian Snowball stemmer over the resulting token list. The stemmer
passes English tokens through unchanged (needed so the EN PDF corpus item
still matches). `rag.bm25_search(rows, query, k=20) -> list[int]`: build
`rank_bm25.BM25Okapi` over the tokenized `user_chunks` rows (T1's
`storage.user_chunks`) **fresh, for this query only** — no persistent
index, no caching across queries (NG-07). Score the tokenized query,
return chunk ids with **score > 0** by descending score then ascending id
— a zero-score row is **dropped**, never ranked last. At most `k`. Empty
corpus or all-zero scores → `[]` (RRF then reduces to the vector list
alone).

## RRF fusion (REQ-V190-RET-05)

`rag.rrf(rankings: list[list[int]], k: int = 60) -> list[int]`: for every
ranking in `rankings`, for every chunk id `d` at its **0-based** position
`rank` within that ranking, `score[d] += 1 / (k + rank)` with `k = 60`
(the default — this is not a config value, it's the RRF constant).
Result: ids sorted by descending score, ties broken by **ascending id**.
`hybrid = rrf([vector_ids, bm25_ids])[:10]` — ten candidates for the
reranker, or the final list when reranking is off or fails.

## LLM listwise rerank, never fatal (REQ-V190-RET-06)

`rag.rerank(llm, *, question, candidates: list[Passage], conn, conv_id,
resolve_cost) -> list[Passage] | None`.

Prompt: system message exactly `"Rank passages by relevance to the
question. Reply with a JSON array of passage numbers, most relevant
first, nothing else."`; one user message with the question and the
candidates numbered `[1]`…`[10]`, each **truncated to 600 characters**.
Call: `llm.complete(messages, None, max_tokens=128, reasoning=<forced
off>, timeout_s=20.0)` through the existing client (failover included,
`llm/failover.py:28-60`).

**Reasoning, forced off, not left to policy.** `reasoning_tag("rerank",
None)` returns `"final"` (`llm/base.py:74-80`'s existing rule: only
`summary` is special-cased, otherwise `"tool-round"` when tools are
exposed else `"final"`). Under the default `LLM_REASONING_ON_PURPOSES =
tool-round` this already resolves to off, but an operator who added
`final` to the on-set would flip it on for the reranker — so the reranker
must call `resolve_reasoning("off", frozenset(), "final")`
(`llm/base.py:126`) **explicitly**, forcing it regardless of the policy
configuration (the policy config itself is untouched, NG-09).

Parse the reply as a JSON array of integers — tolerate a fenced code block
or surrounding prose by extracting the first `[`…`]` substring. Result:
the candidates in that order, followed by any candidate the array omitted,
in their original RRF order. **Any** failure — `LLMError`, timeout, an
unparsable reply, an index outside `1…len(candidates)`, a duplicate index
— returns `None`. Recorded in `llm_calls` with `purpose="rerank"`,
`round=0`, `attempt=1`, `turn_id=None`, inside a `chat` CLIENT span,
**through `agent._record_llm_call`** (`agent.py:910` region) — the same
function the summary path uses.

## The `Searcher` (REQ-V190-RET-07) — exact pipeline order and fallback contract

`rag.Passage` — frozen dataclass `(chunk_id, filename, page: int | None,
chunk_index, text)`. `rag.Searcher(conn, *, user_id, embedder, llm, cfg,
conv_id, resolve_cost)` exposes `search(query: str) -> SearchResult`:

```python
SearchResult(
    passages: list[Passage],
    documents_present: bool,
    rerank_attempted: bool,
    rerank_succeeded: bool,
    rerank_failure: str | None,
)
```

**The three rerank fields are the only sound proof the reranker ran** —
get their semantics exactly right, later tasks (T8's eval, in particular)
gate on them:

- `rerank_attempted = True` **exactly when** step 4 below is entered:
  `cfg.rag_rerank == "on"` **and** ≥ 2 candidates. Otherwise all three
  fields are `False`, `False`, `None`.
- `rerank_succeeded = True` **only after** the validated order **and all
  required bookkeeping** have completed — reply parsed, every index valid
  and distinct, reordered list built, **and** `_record_llm_call`, span
  finalisation, `resolve_cost` **all returned**. It is the **last**
  assignment on the success path; anything that raises or returns `None`
  before it leaves it `False`.
- `rerank_failure` — `None` on success, else a short **redacted** reason
  string (same text the warning carries). **Never rendered to the model**
  — T6's tool envelope is built from `passages` alone, unaffected by these
  three flags.

Pipeline, this **exact order** (hydration before reranking, since `rerank`
needs each passage's filename/text):

1. Vector retrieval (RET-03) and BM25 retrieval (RET-04), each ≤ 20 ids.
2. RRF fusion (RET-05) down to at most ten chunk ids.
3. **Hydrate** those ten ids through `storage.chunks_by_ids` (T1) and
   **restore the RRF order** over the returned rows — the DB's row order
   must never reorder the candidates. Exactly one `chunks_by_ids` call per
   `search`, no more.
4. Rerank the hydrated `list[Passage]` (RET-06) when `cfg.rag_rerank ==
   "on"` and ≥ 2 candidates. **Any** rerank failure falls back to the
   hydrated RRF order from step 3. **The fallback boundary is the whole
   optional operation, not just the model call**: wrap the `rerank`
   invocation **and all of its bookkeeping** —
   `agent._record_llm_call`, span finalisation, `resolve_cost`, warning
   formatting, anything else on the rerank path — in **one** `try/except
   Exception`; on any exception, return the step-3 order with
   `rerank_succeeded=False` and `rerank_failure` set. The warning itself
   (`log.warning("rerank fell back to rrf order: <reason>")`, redacted)
   must be emitted **inside its own guarded block**, so a failing logger
   or a failing call recorder cannot escape into the answer either.
5. Slice to the first `cfg.rag_top_k` (default K=5).

`documents_present = storage.document_count(conn, user_id=user_id) > 0`
(T1's API). `Searcher` keeps `self.calls: list[SearchResult]` — every call
of the turn, in order (T6's attribution logic reads this). `user_id` is
bound at construction (by `bot.py`, T7's job) and is **not** a parameter
of `search`.
