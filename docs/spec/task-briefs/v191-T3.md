|---|---|---|

`google/gemma-3-12b-it` is served by a single upstream, and that upstream
rate-limits a burst: `{"error":{"message":"Provider returned error","code":429}}`.
Gate 7 issues its rerank calls back to back, so most of them 429.

**The deeper defect is ours, not OpenRouter's.** `llm/base.py:401` already
classifies a 429 as `retryable=True`. `rag.rerank()` catches `LLMError` and
returns `None` **without ever reading that flag** (`rag.py:236-243`), so a
transient, explicitly-retryable upstream error degrades silently to RRF order
and takes the gate down with it. The classification exists; rerank ignores it.
Fixing only the model would leave that intact and make a green gate 7 a
property of somebody else's rate limiter.

## What to change — code, tests and `.env.example` only

### 1. `rag.py` — honour `retryable`

`rerank()` retries a failed call when and only when the raised `LLMError` has
`retryable=True`. Bounded:

- `_RERANK_MAX_ATTEMPTS = 3` (one initial try plus two retries).
- Backoff before retry: **0.5 s, then 1.5 s**, as a module constant, not a
  literal buried in the loop.
- A non-retryable `LLMError`, or an unparsable reply, is **not** retried —
  those are not transient and a retry only burns the budget. Keep today's
  behaviour for them exactly: return `None`, fall back to RRF, set
  `rerank_succeeded=False` with a non-empty `rerank_failure`.
- Exhausting the attempts behaves like today's single failure: `None`, RRF
  fallback, flags set. The gate must still be able to see a real outage.
- `_RERANK_TIMEOUT_S` 30.0 → **10.0**. Measured median is 0.95 s and a 429
  comes back fast; 10 s per attempt keeps the worst case per item near 32 s so
  three attempts still fit inside a sane gate budget. State that arithmetic in
  the comment.

Log each retry at the level the module already uses for
`"rerank fell back to rrf order: %s"`, with the attempt number and the
error — a silent retry is how a degraded route hides.

### 2. `.env.example` — change the recommended route

with a one-line comment saying why: best measured recall among the models
that survive a burst, and a single-upstream model was what broke T1. The

### 3. Tests

- A retryable `LLMError` on attempt 1, success on attempt 2 → `rerank`

- A non-retryable `LLMError` → exactly **one** call, no retry, RRF fallback.
- Three retryable failures → exactly three calls, RRF fallback, flags set,

- An unparsable reply → one call, no retry.
- The backoff constants and `_RERANK_MAX_ATTEMPTS`/`_RERANK_TIMEOUT_S` are

## Amendment — 2026-09-12: `_RERANK_TIMEOUT_S` 10.0 -> 15.0

The first pass of this brief shipped `_RERANK_TIMEOUT_S = 10.0`. Gate 7 was
then run twice concurrently with gate 6 (`devtools/mutation_check.py`, which
rewrites `rag.py` on disk per mutation and restores it afterward) — both
runs are void: `rag_eval.py` could import `rag.py` mid-mutation, including
mid-mutation of the retry gate itself, and both runs showed a many-429s,
many-RRF-fallback pattern consistent with that. A clean isolated re-run
(gate 7 alone, nothing else touching the tree) passed 10/10.

To settle whether 10.0 itself had real headroom, three further gate 7 runs
were made, strictly sequential, `rag.py`'s sha recorded and verified
identical before and after each: exit 0, 429-lines 0, failed-items 0, each
run ~2m10s. All three showed the identical shape: one item's rerank call
times out on attempt 1 (10.0s) and again on attempt 2 (10.0s), succeeding
only on attempt 3 — every one of those passing runs had zero retry budget
left. That is real, uncontaminated evidence of a too-tight timeout, not a
repeat of the concurrency artifact above.

Change, on that evidence: `_RERANK_TIMEOUT_S` 10.0 -> 15.0 (worst case per
item: `3 * 15.0 + (0.5 + 1.5) = 47.0s`, up from `32.0s`). The model
recommendation in `.env.example` (`mistralai/mistral-small-24b-instruct-2501`)
is unchanged and confirmed — the earlier apparent 429/quota signal against
it was the same concurrency artifact, not a real model problem. Also added:
a retry that succeeds is now logged (attempt number, the successful call's
own elapsed seconds) at the same level as a retry that fails, so a future
gate 7 run can show its own margin against this constant without needing
another special investigation.
