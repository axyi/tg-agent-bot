## Part 1 — redaction + truncation helper (REQ-V180-SEC-01, -02 item 1)

Write one shared helper in `dashboard_server.py` (it can import `config`,
unlike `dashboard_render.py`) that takes one `messages` row (from
`storage.conversation_messages`: `turn_id, role, content, tool_call_id,
created_at, id`) and returns a redacted, truncated representation used
identically by **both** the HTML and JSON routes:

- `config.redact()` applied to **all three** message-derived fields:
  `content`, `role`, `tool_call_id` (SEC-01 — a test will inject a secret
  into all three and expect it gone from all three, on both routes).
- `content` truncated to **2000 characters of the redacted plain text**,
  **before any escaping** — `redact()` then the cut, so both sinks (HTML
  escapes after this, JSON doesn't escape at all) cut at the identical
  boundary. When truncation actually occurred (redacted content longer
  than 2000 chars), append a marker plus the original length as a note —
  exact wording is yours to choose (no literal string is specified by the
  spec), but it must be **additional to** the 2000 (not counted inside the
  per-message cap) and it **is** counted by the page's overall byte budget
  when rendered.
- This is the **one** place redaction happens — `dashboard_render.py`
  stays pure and only escapes (HTML sink) or isn't touched at all (JSON
  sink, which needs no escaping, `json.dumps` does its own).

## Part 2 — the four routes (REQ-V180-CONV-06, -07)

1. **`GET /conversations`** (`_page_conversations`, your name): parse
   `limit` via `_parse_limit(params, 50, is_api=False)` (only `limit` is an
   allowed query param — mirror `_parse_query`'s `allowed` set), connect
   read-only, call `storage.recent_conversations(conn, limit=limit)`,
   render via `dashboard_render.conversation_list_section(rows)`, wrap in
   `dashboard_render.page(...)` with the one required line of copy — *"A
   conversation is one `/new`-to-`/new` stretch of chat; this is the list
   of them."* — placed however reads best (T5 left this choice to you).
   Nav: `[("usage", "/"), ("traces", "/traces"), ("tools", "/tools"),
   ("conversations", "/conversations")]`.

2. **`GET /conversations/<id>`** (`_page_conversation`, your name): id
   validated `1 ≤ n ≤ 2**31 - 1` by your new `_CONV_PAGE_RE` (below);
   parse `limit` (`_parse_limit(params, 200, is_api=False)`) and `cursor`
   (your new `_parse_cursor`, see above). Call `storage.conversation_row`
   first — `None` → 404 via `_not_found(is_api=False)` (an id syntactically
   valid but naming no row). Otherwise call
   `storage.conversation_messages(conn, conv_id, limit=limit, cursor=cursor)`
   — catch its `ValueError` (unmatched cursor) and turn it into
   `_bad_request("cursor", is_api=False)`. Redact+truncate every returned
   row (Part 1's helper). Compute the trace-link map via
   `storage.conversation_turn_traces(conn, conv_id, turn_ids)` for the
   turn ids actually in the page. Render the page shell **twice** — once
   with an empty/placeholder body to measure `chrome_bytes` (UTF-8 length
   of `dashboard_render.page(...)` with everything except the transcript
   rows), then call `dashboard_render.conversation_transcript_section(...)`
   with that measured `chrome_bytes`, and assemble the final page. An
   existing conversation with zero messages renders the empty state at 200
   (not 404). Nav includes `("conversations", "/conversations")` as
   established above.

3. **`GET /api/conversations`** (`_api_conversations`, your name): mirrors
   `_api_traces`'s shape exactly — same `limit` parsing (`is_api=True`),
   same query, payload `{"limit": limit, "conversations": [...]}` with
   each row through your `_conversation_row_json` helper, `_respond_json`.

4. **`GET /api/conversations/<id>`** (`_api_conversation`, your name):
   mirrors `_api_trace`'s error shape (404/400 with `is_api=True`) plus
   CONV-06's own payload: `{"conv": conv_id, "limit": limit, "cursor":
   cursor_echo, "next_cursor": ..., "messages": [...]}`. `cursor` in the
   payload **echoes the request parameter** (`null` when absent, else the
   `"turn_id-id"` string or `[turn_id, id]` — your call, be consistent).
   `next_cursor` is **the page's own emitted cursor** (what the byte
   budget or the reader actually stopped at — same value the HTML route's
   next-link would carry), `null` at the end of the conversation. **No
   `has_more` key anywhere.** A turn the page's byte budget split carries
   `"continued": true` on its **last** message object.

   **Critical: this route does NOT call `conversation_transcript_section`**
   (SEC-02: "the JSON route does not go through the HTML builder, so it
   applies the same budget to its own serialized rows before
   `_respond_json`"). You must implement the **same atomic-turn-admission
   algorithm** (CONV-04's steps: measure a whole turn's rendered bytes —
   here, its **JSON-serialized** bytes via your own `_dumps`-shaped
   measurement — admit whole if it fits, stop if the page already holds a
   turn, split only if the page is empty) **again, independently, against
   JSON bytes** instead of HTML bytes. Seed the accumulator with the
   JSON envelope's own measured byte size (the fixed keys, the `conv`/
   `limit`/`cursor` values) plus `TRANSCRIPT_PAGE_SUFFIX_BYTES`. Factor
   this into a small shared helper if you can reuse the turn-grouping
   logic between the two sinks (grouping messages by turn, computing
   per-turn sizes against a caller-supplied renderer callback) — your
   design choice, but do not silently skip this half of SEC-02 because
   the HTML side already has it; the JSON side needs its own, independently
   correct implementation.
